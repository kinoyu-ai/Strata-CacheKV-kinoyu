# V100用Split Engineの実験版

**全エキスパートがVRAMに入らなくても、RAMへ退避して動かせます。** このブランチは上流0.2.12のSplit EngineをLinux・CUDA 12.9・V100 16 GiB × 2で使うための実験版です。Autoの対象GPUは変更しません。

上流にもRAM退避はありますが、動的な配置変更のため全エキスパートのRAMコピーを保持します。検証機のUD-IQ3_XXSでは約47.5 GiBあり、さらに約26.8 GiBのPLEテーブルを固定すると搭載RAM約54.9 GiBを超えます。起動判定を外すだけでは足りませんでした。

この版は、次の2つを明示的に選べるようにします。

- **PLEの直接読み出し**：大きなNgramテーブルをRAMへ固定せず、必要な行だけ読みます。RAM行キャッシュと複数ドライブのディスクキャッシュを併用できます。
- **エキスパートの固定配置**：頻度に応じてRAMとVRAMへ配置し、GPUに置いた重みのRAMコピーを省きます。各サイズの重みを処理する小さなGPUキャッシュは残し、計算時に使う重みを読み込みます。KV領域へ重みの領域を貸し出すArenaは使いません。

通常エンジンのディスクKV退避は、この別エンジンには移植していません。Splitの会話キャッシュはRAMのみで、KV形式はint8です。通常版の`k8v4`や「RAM→Optaneの会話KV退避」が必要な場合は[main](https://github.com/kinoyu-ai/Strata-CacheKV-kinoyu/tree/main)を使ってください。

## 別ビルドの作成

```sh
B="$PWD/build-split-v100" CUDA=/usr/local/cuda-12.9 \
GG=/path/to/pinned/llama.cpp JOBS=4 packaging/build_split_v100.sh
```

`GG`には`third_party/ggml/VERSION.txt`に記載されたコミットのllama.cppを指定します。出力は`build-split-v100/split/strata-split-2`です。2枚構成、MTP用で、DFlash2はこの独立ビルドに含みません。CUDA 13ではV100向けにコンパイルできません。

## 設定

このブランチのPython側を使用する場合、通常の起動設定に以下を追加します。

```json
{
  "split_engine": "on",
  "split_expert_ram_gib": 36,
  "split_fixed_experts": true,
  "split_conversation_cache_mib": 2048,
  "parallel": 1,
  "env": {"FNX_PF_ROWS": "4096", "FNX_PF_PASS": "2"}
}
```

これは**設定に追加する項目**です。モデル・MTP・認証等を含む設定全体ではありません。通常の`args`には`--native`と`--mtp`が必要です。既存の`--max-context`を`32768`、KVを指定している場合はその値を`int8`へ変更します。同じ引数を重複して追加しないでください。別ビルドを通常エンジンの隣へ置き、`draft_vocab_en.bin`を通常のdataディレクトリーへ用意してください。必要なファイルやメモリがない場合は通常エンジンへ戻ります。実際の起動エンジンをログで確認してください。

`args`に次も追加します。保存先は、マウント済みドライブ上に自分のユーザーが所有するディレクトリーを事前に作成してください。他のユーザーが書き込めるディレクトリーは使えません。

```json
[
  "--ple-io", "direct",
  "--ple-row-cache", "65536",
  "--ple-disk-cache", "/mnt/cache-a/ngram", "12288",
  "--ple-disk-cache", "/mnt/cache-b/ngram", "12288"
]
```

ディスク指定は省略可能です。その場合もモデルファイルから必要な行だけ読みます。`--ple-row-cache`はRAMに保存する行数、各ディスクの末尾の数値はMiB単位の容量です。追加したPLE機能は未指定なら無効で、上流どおりテーブルをRAMへ固定します。ディスク上のページはプロセス単位の一時キャッシュです。

エンジンを直接指定する設定では、対応する環境変数を使えます。

```json
{
  "FNX_ARENA": "0",
  "FNX_EXPERT_RAM_GIB": "36",
  "FNX_FIXED_EXPERTS": "1",
  "FNX_PF_ROWS": "4096",
  "FNX_PF_PASS": "2"
}
```

`FNX_EXPERT_RAM_GIB`はエキスパートのうちRAMへ置く量です。会話KVキャッシュの容量ではありません。`FNX_FIXED_EXPERTS=1`は`FNX_ARENA=0`と数値の`FNX_EXPERT_RAM_GIB`を必要とします。`FNX_PF_ROWS=4096`と`FNX_PF_PASS=2`は検証機でPrefill用のVRAM使用量を抑える設定です。片方だけを指定すると自動調整が無効になるため、両方を指定します。ホルダーへの接続と、起動後の重み再配置には対応しません。VRAMが不足する場合はRAMへ置く量を増やして再起動します。

## 検証範囲

検証結果と速度は以下に記録します。すべてのGPU、モデル、長さ、並列数での動作保証ではありません。特に他のバックエンド、画像、DFlash2、複数の同時リクエストは今回検証していません。

### 2026-11-08の実機確認

V100-SXM2 16 GiB × 2、RAM 56,196 MiB、Linux、CUDA 12.9 / sm_70、各GPU 150 Wで、Qwen3.8-Flash-Next Unsloth Dynamic v3.1 UD-IQ3_XXSを読み込み、回答生成まで確認しました。設定は上記の32k・並列1・RAM重み36 GiB・RAM会話キャッシュ2 GiB・PLE行キャッシュ65,536行・Ngramディスク12 GiB × 2です。MTP K=4、KVはint8、Prefillは4,096行 × 2パスです。

合成入力Aは3,125トークンで、同じ短い文を512回繰り返した本文と、指定文字列を返す指示からなります。各ケース1回、temperature 0、top-k 1、seed 42、Thinkingオフで測定しました。OSページキャッシュは消去していません。

| ケース | 再利用トークン | Prefill時間 | 回答 |
| --- | ---: | ---: | --- |
| 会話Aの初回 | 0 | 17.38秒 | ORCHID731 |
| 別の短い会話の後、Aへ復帰 | 3,118 | 1.68秒 | ORCHID731 |

時間はAPIの`timings.prompt_ms`で、回答生成時間を含みません。エンジンのログでは、RAMの状態読み込みそのものは91 msでした。表の1.68秒には、残り7トークンの処理なども含まれます。これはSplit内でのRAM会話キャッシュの測定で、通常版との速度比較やディスクKV復元の測定ではありません。

指定文字列、17 + 25、日本語文の復唱の3件も期待する回答と一致しました。MTPの採用を確認し、Aの初回・復帰はともに7候補中4候補を採用しました。各GPUの各エキスパートについて先頭・末尾32バイトを元データと照合し、直接読み出しで使ったPLE行も従来のマッピングから読んだ行と全バイト一致しました。これらの検査は任意の`FNX_FIXED_VERIFY=1` / `FNX_PLE_VERIFY=1`で実施し、通常の設定では無効です。

起動直後のVRAM空きはGPUごとに738 / 978 MiBでした。余裕は大きくないため、GPUを使う他のアプリや設定変更によっては起動できません。RAM全体の空きは起動時に約9 GiBありました。上記の短い試験は長期安定性や一般的な回答品質の評価を代替しません。

通過した自動確認は、起動判定・プロトコル等のPythonテスト76件、C++テスト4件（PLEの90/170バイト行、境界・重複・再オープン・2つのディスク保存先等を含む）、不正なPLE引数の拒否4ケース、CUDA peer APIを参照しないことの確認です。MTP独立版のCUDAビルドを検証しました。DFlash2ありの経路は構文検査のみで、HIP/SYCL/Metalの再ビルド・実行は行っていません。

失敗した設定もあります。全エキスパートのRAMコピーを残す方式では、この検証機のドライバーがメモリ確保に失敗しました。また、`FNX_PF_PASS=2`のみを指定すると8,192行が選ばれてVRAM不足になりました。上記の固定配置と4,096行・2パスの組み合わせで起動・推論・RAM復元を確認しています。
