# Ngram（PLE）テーブルのディスクキャッシュ

Ngramテーブルから読んだ4 KiBページを、指定したディスクに一時保存する機能です。
既存のRAM行キャッシュを先に参照し、そこにないデータをディスクキャッシュ、元のモデルファイルの順に探します。
**初期状態はOFFです。会話KVキャッシュとは別の機能です。**

## 設定

このForkからビルドしたエンジンを使い、モデル設定の `args` に以下を追加して再起動してください。
同じ引数が既にある場合は置き換えます。これは設定の一部です。

```json
[
  "--ple-io", "direct",
  "--ple-row-cache", "1048576",
  "--ple-disk-cache", "/mnt/cache-a/strata-ngram-cache", "12288",
  "--ple-disk-cache", "/mnt/cache-b/strata-ngram-cache", "12288"
]
```

`--ple-disk-cache PATH MIB` は繰り返し指定できます。容量は**ディレクトリごと**です。
例は各12 GiB、合計24 GiBです。1台だけでも使えます。ページ番号で保存先を振り分け、各保存先で
ハッシュ方式の置き換えを行います。RAIDの設定やモデルファイルの移動は行いません。

保存先は実際のマウント先に置き換え、先にサービスユーザー所有の専用フォルダを作ってください。
他ユーザーが書き込めるフォルダは使用できません。同じフォルダを複数のエンジンで同時使用することもできません。
マウントされていない場合にOSディスクへ書かないよう、キャッシュ用のフォルダは自動作成しません。
モデルの元ファイルは残してください。テーブル全体がディスクキャッシュに収まる必要はありません。

## RAM・KVとの違い

| 設定 | 保存内容 | 単位 |
| --- | --- | --- |
| `--ple-row-cache` | NgramのRAM行キャッシュ | 行数。`0`で無効 |
| `--ple-disk-cache PATH MIB` | Ngramのディスクページキャッシュ | 保存先ごとのMiB。`0`でその保存先を無効 |
| `--conversation-cache-mib` | 別会話のKV・実行状態をRAMへ退避 | MiB |
| `--conversation-cache-disk-mib` | 別会話のKV・実行状態をディスクへ退避 | MiB |

設定と容量は独立しています。同じドライブに両ディスクキャッシュを置く場合は、容量の合計と空き容量を考慮してください。
この機能はNgramテーブルの読み出しを対象にしています。KV復元でPrefillを省略する機能とは効果が異なります。

## データと障害時の扱い

- Linuxの `--ple-io direct` 向けです。`mmap` / `ram` とは併用できません。
- 256 MiB以下の分割ファイルへ保存します。対応する直接I/Oを使い、ディスクデータ全体をRAMに複製しません。
- 読み出しを最大16ワーカーで並列化し、キャッシュへの書き込みはバックグラウンドで行います。
  書き込み待ちデータは最大16 MiBに制限し、混雑時は追加の保存を省略します。
- RAMには検索用情報を持ちます。各12 GiBの2保存先で約144 MiBに加え、少量のファイル管理情報が必要です。
- キャッシュヒットではチェックサムを確認します。破損はミスとして扱い、元ファイルから再取得します。
- 空き容量不足・直接I/O非対応・ディスク障害ではディスクキャッシュを無効にし、元ファイルの読み出しを続けます。
- プロセス単位の一時保存です。正常終了時に削除し、異常終了の残骸は次回の排他ロック取得後に削除します。再起動後の再利用は行いません。
- 起動時に保存先と上限を、利用中・終了時にはヒット、ミス、書き込み、破損、失敗件数を標準エラーへ記録します。

## 無効化

すべての `--ple-disk-cache` とそれに続く保存先・容量を削除して再起動します。
`--ple-row-cache` や会話KVキャッシュを変更する必要はありません。

## 検証

モデル・GPU不要のテスト：

```sh
g++ -std=c++20 -O2 -pthread -I include \
  src/ngram/ple_disk_cache_test.cpp src/ngram/ple_reader.cpp \
  src/platform/direct_file.cpp -o /tmp/ple-disk-cache-test
/tmp/ple-disk-cache-test
```

既存の書き込み可能な保存先を2つ渡すと、その中にテスト専用フォルダを作って実際のドライブでも確認できます。
テスト専用フォルダだけを終了時に削除します。

```sh
/tmp/ple-disk-cache-test /mnt/cache-a/strata-ngram-cache /mnt/cache-b/strata-ngram-cache
```

2保存先、容量上限と置き換え、チェックサム不一致、読み出し失敗、排他、正常・異常終了後の清掃、
90 / 160 / 320バイト行とページ境界、I/Oワーカーの有無を確認します。
キャッシュOFF、初回、ヒット後の入力データが同一であることも確認します。

ストレージや接続方式によっては、キャッシュの読み書きで遅くなることがあります。
実モデルでの速度向上や、他のバックエンドでの動作は保証しません。元のKVキャッシュのベンチマークを、この機能の測定結果として扱わないでください。

## 今回確認した範囲

公開用v0.2.10ソースのCPUテスト8件（既存KVテストを含む）、既存PLE selftestの8形式、
AddressSanitizer / UndefinedBehaviorSanitizer、非PIEビルドのThreadSanitizerが通過しました。
USB接続の2台のext4保存先でも、ページの一致と障害時の切り替えを確認しています。
通常のPIE版ThreadSanitizerはホストのメモリマッピング制約で起動できなかったため、非PIE版で検査しました。

稼働環境では同じ変更をStrata 0.2.11へ適用してCUDA版をビルドし、2枚のV100、
Qwen3.8-Flash-Next Unsloth v3.1 UD-IQ3_XXS、KV k8v4、MTPで回答一致を確認しました。
公開用v0.2.10のエンジン本体は今回のCUDAコンパイル設定で構文検査を通しています。
他バックエンドでのビルド・実行、保存先を合計24 GiBまで満杯にする実機試験は未実施です。

このUSB接続では、RAM行キャッシュを無効にした4,096件の読み出し単体試験で、
元NVMeが約37〜40 ms、ディスクキャッシュのヒット後が約66〜67 msでした。
この条件では高速化していません。これはPrefillや応答全体の時間ではなく、読んだデータは全条件で一致しました。
保存先は各512 MiB、90バイト行、無作為位置、読み出し完了までを測定し、バックグラウンド書き込み完了待ちは含めていません。
CPUビルドと並行した参考値で、速度向上の根拠にはしていません。
